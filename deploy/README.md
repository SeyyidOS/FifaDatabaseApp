# Self-hosted deployment

Runs Matchnight on this server behind the shared Caddy proxy (the one that serves MLflow), at
**https://matchnight.hotspotkeeper.com**. Caddy handles HTTPS; this folder only adds a site block
(`Caddyfile.fifa`). Its first address is the site's one address; the old
`fifa.173.249.40.69.sslip.io` only redirects there (308, same path), because browsers keep sign-ins
and invites per address. To move to another domain, point its A record at this server (DNS only, no
proxy), put it first in `Caddyfile.fifa`, add the current one to the redirect block, and change
`APP_URL` in secrets.env to match.

| Container  | What it is                                                     | Networks                      |
|------------|-----------------------------------------------------------------|-------------------------------|
| `fifa_web` | nginx: the built React app, the `/api` proxy, and the API's way out for e-mail | `mlflow_net`, `fifa_internal` |
| `fifa_api` | the FastAPI backend (`backend/`); match photos in `/root/programs/fifa-app/photos` | `fifa_internal` (no internet) |
| `fifa_db`  | Postgres 16, data in `/root/programs/fifa-app/pgdata`           | `fifa_internal` (no internet) |

```bash
deploy/deploy.sh                 # publish or update by hand (backs up first; safe to re-run); normally auto-deploy.sh does it
deploy/deploy.sh --backup        # gzipped SQL dump into /root/programs/fifa-app/backups (root's crontab runs it nightly at 04:07)
deploy/deploy.sh --passwords     # first passwords of the "main" board (the original group)
deploy/deploy.sh --admin-key     # server admin key: works as admin on every board
deploy/deploy.sh --test-mail TO  # send a test e-mail with the mail settings below
deploy/deploy.sh --import FILE   # first run only: load a plain SQL dump into the empty database
deploy/deploy.sh --remove        # unpublish; containers go, data stays
```

## Boards and access

Anyone can create a board from the home page. Each board has its own players, matches, standings,
K-factor and club ratings (one list per game, e.g. FC26 and FC27). With accounts on (`ACCOUNTS=on`
below), a new league belongs to the account that starts it and has no passwords: people come in with
invite links. Boards from before accounts, and every board while accounts are off, have two passwords:

- the **board password**, shared with the group: view everything, add players, log matches;
- the **admin password**: archive or delete, rename, change the K-factor and the passwords.

Signing in returns a token the browser keeps ("Remember this device"), so a device stays signed in.
Changing a password in Settings signs out the devices that used the old one. Wrong passwords are
limited to 10 per 15 minutes per address, new boards to 5 per hour.

The data from before boards existed lives in the board `main` (`#/b/main`); old links redirect there.

## Secrets

`/root/programs/fifa-app/secrets.env` (mode 600; missing values are generated by the script):

| Variable                       | Purpose                                                        |
|--------------------------------|----------------------------------------------------------------|
| `POSTGRES_PASSWORD`            | database password                                              |
| `SECRET_KEY`                   | signs device tokens; changing it signs every device out        |
| `ADMIN_KEY`                    | server admin key (`X-Admin-Key` header), admin on every board  |
| `LEGACY_BOARD_PASSWORD`        | first board password of `main` (used once, by the migration)   |
| `LEGACY_BOARD_ADMIN_PASSWORD`  | first admin password of `main` (used once, by the migration)   |

Optional, for accounts (none of them is generated; a deploy picks up changes):

| Variable        | Purpose                                                                          |
|-----------------|----------------------------------------------------------------------------------|
| `APP_URL`       | where sign-in links point: the first address in `Caddyfile.fifa`, e.g. `https://matchnight.example.com/` |
| `ACCOUNTS`      | `on` to offer accounts (backend/README.md, "Accounts"); needs `APP_URL` and mail |
| `SMTP_HOST`     | the mail server, e.g. `smtp.resend.com`; `SMTP_PORT` (587), `SMTP_USER`, `SMTP_PASSWORD` |
| `MAIL_FROM`     | the sender, in quotes when it has a name: `MAIL_FROM="Matchnight <giris@mail.example.com>"` |
| `SUPPORT_EMAIL` | where people write for help: shown on the Support page (`/support`); no contact line while it's unset |
| `REVIEW_EMAIL`, `REVIEW_CODE` | App Review's demo account: that address signs in with that six-digit code and is sent no e-mail. `deploy/review-league.py` gives it a league to look at |

`EDITION` (optional, `classic` when unset) picks what the site shows:
- `classic` is the app as the original group knows it.
- `store` leaves out what isn't ours to publish: real club crests, card ratings, the cards' squads and faces, and the game's season names. It is what the App Store app always runs.

To switch, change the line in secrets.env and redeploy the settings:

    cd /root/programs/fifa-app/repo && APP_VERSION=$(git rev-parse --short HEAD) ./deploy/deploy.sh

The data stays the same either way, so switching back is just as quick. `backend/edition.py` and
`frontend/src/lib/edition.ts` say what each edition shows, and the API and `/edition.js` (nginx) both read
the setting. The tag `classic-2026-10-20` keeps the code as it was before the editions.

The API has no internet. It sends mail through `fifa_web`, which passes the connection on to `SMTP_HOST`
untouched (`frontend/nginx/smtp-relay.conf.stream-template`); TLS runs between the API and the mail server
and is checked against `SMTP_HOST`'s certificate. Quote any value with spaces: the file is read by both
the shell and Docker Compose.

## Continuous deployment

The server publishes `main` by itself: a systemd timer runs [`auto-deploy.sh`](auto-deploy.sh) every
minute in a clean clone at `/root/programs/fifa-app/repo` (never in a working copy). When `main` has
a new commit and its GitHub Actions checks (`backend`, `frontend`) have passed, it runs `deploy.sh`
for that commit: database backup, build, restart, smoke test. If that fails, the commit that was live
before is published again. A commit whose checks or deploy failed is skipped; the next commit on
`main` is tried as usual. It only reads from GitHub (the repository is public), so no credentials for
it are stored here.

```bash
/root/programs/fifa-app/repo/deploy/auto-deploy.sh --status   # live commit, waiting, skipped, last log lines
journalctl -u fifa-auto-deploy -n 50                          # the timer's runs
systemctl list-timers fifa-auto-deploy.timer                  # when it runs next
```

Set up once (already done on this server):

```bash
git clone https://github.com/SeyyidOS/FifaDatabaseApp.git /root/programs/fifa-app/repo
cp /root/programs/fifa-app/repo/deploy/systemd/fifa-auto-deploy.* /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now fifa-auto-deploy.timer
```

To stop publishing for a while: `systemctl stop fifa-auto-deploy.timer` (`start` to resume). To go
back to an older commit, revert it on `main` through a pull request; restoring the database from
`backups/` is manual (`gunzip -c FILE | docker exec -i fifa_db psql -U fifa -d fifa_db` into an
empty database).

Match photos are files in `photos/` (owned by the API's user, uid 10001), not in the database, so the
dumps in `backups/` stay small and don't include them. Deploys never touch that folder. Only uploads to
`/api/boards/*/matches/*/photos` may be larger than 64 KB (up to 12 MB), in `Caddyfile.fifa` and in the
web container's nginx.

## Off-server backups

The nightly dump (`deploy.sh --backup`, 04:07) stays on this server's disk. [`offsite-backup.sh`](offsite-backup.sh)
copies it and the photos to a Backblaze B2 bucket, so a lost disk or server doesn't take the leagues
with it:

- the newest dump of the night, as `db/fifa_db-….sql.gz.age`, the last 30 kept;
- `photos/` (match photos and account photos), as `photos/photos-YYYYMMDD.tar.age`, the last 7 kept.

Both are encrypted here with [age](https://age-encryption.org) before they leave, to a public key. The
private key that opens them must **not** stay on this server: keep it in a password manager, say. Both
tools run from pinned Docker images (`rclone/rclone:1.71.2`, `alpine:3.22` with age); nothing is
installed. Until all of the settings below are in `secrets.env` the script says which one is missing
and exits 0, so it can be in the crontab before the bucket is ready. B2's free tier (10 GB) is far more
than this needs.

| Variable | What |
|---|---|
| `BACKUP_KEY_ID` | the B2 application key's *keyID* |
| `BACKUP_KEY` | the B2 application key itself (shown once, when it is made) |
| `BACKUP_BUCKET` | the bucket's name, e.g. `matchnight-backups` |
| `BACKUP_AGE_RECIPIENT` | the age public key, `age1…` |
| `BACKUP_S3_ENDPOINT` | optional: any S3-compatible store instead of B2, with the same key id, key and bucket |

To set it up:

1. In Backblaze B2: a **private** bucket (region EU Central), and an application key with *Read and
   Write* access to that bucket only. Pruned backups are deleted for good (`hard_delete`), so the
   bucket's default lifecycle ("keep all versions") doesn't make them pile up.
2. Make an age key pair; the private part goes off the server and is deleted here:

        docker run --rm alpine:3.22 sh -c 'apk add -q age && age-keygen' > /root/backup-key.txt
        grep 'public key' /root/backup-key.txt   # the age1… line is BACKUP_AGE_RECIPIENT

3. Add the variables to `secrets.env`, then run it once by hand:

        /root/programs/fifa-app/repo/deploy/offsite-backup.sh

4. Run it after the nightly dump: in root's crontab, the backup line becomes

        7 4 * * * /root/programs/fifa-app/repo/deploy/deploy.sh --backup >> /root/programs/fifa-app/backups/cron.log 2>&1 && /root/programs/fifa-app/repo/deploy/offsite-backup.sh >> /root/programs/fifa-app/backups/offsite.log 2>&1

To check that a backup really comes back, [`restore-drill.sh`](restore-drill.sh) loads a dump into a
throwaway Postgres, prints the rows per table and the schema version, then removes it. It never
touches the live database.

    deploy/restore-drill.sh --latest /path/to/backup-key.txt          # the newest dump in the bucket
    deploy/restore-drill.sh backups/fifa_db-20261025-040701.sql.gz     # a dump on this server

A real restore loads the same way into the live database, after taking a fresh dump of what's there and
emptying it (the API stopped meanwhile):

    deploy/deploy.sh --backup
    docker stop fifa_api
    docker exec fifa_db psql -U fifa -d postgres -c 'DROP DATABASE fifa_db' -c 'CREATE DATABASE fifa_db OWNER fifa'
    gunzip -c DUMP.sql.gz | docker exec -i fifa_db psql -q -U fifa -d fifa_db
    docker start fifa_api

Photos come back with `age -d -i KEY photos-….tar.age | tar -xf - -C /root/programs/fifa-app`, owned by
uid 10001 as before (`chown -R 10001 photos`).

## Match stats from photos

The stats of a match (possession, shots, xG, …) are read from photos of the game's summary screen by
Claude Code on this server, with the server owner's Claude subscription (no API key, no cost per
photo). `deploy/match-stats.py pending` lists the photos of recent matches without stats, each with
the match (clubs, score, players by side) and a JPEG copy to read; `deploy/match-stats.py submit FILE`
saves what was read through the API with the server admin key (the key never leaves the script).

Photos are read soon after they are uploaded. Root's crontab runs `deploy/match-stats-watch.sh` every 10
minutes:

    */10 * * * * /root/programs/fifa-app/repo/deploy/match-stats-watch.sh

It asks the database whether photos no read has tried yet are waiting (`match-stats.py count --new --ids`,
a quarter of a second). Only then does it start `claude -p` with `deploy/match-stats-prompt.md`, outside any
project, with just the tools it needs. Each photo is tried once, saved or skipped
(`/root/programs/fifa-app/stats-ocr-tried`), so an unreadable one doesn't cost a read every 10 minutes.
A night's stats, and so its Night Post, are complete minutes after its last photo. What each read did is
in `/root/programs/fifa-app/stats-ocr.log`. A read can also be asked for at any time.
